# AI 调用、图像定位与评分保存

这份说明用于客户演示、开发对接和本地排障。当前实现是独立 Go 服务调用自己配置的图片模型；不依赖 yx 平台，也没有专用金相检测器或像素分割模型。结构校验通过表示结果符合本项目的数据规则，不表示专业判断已经得到实验验证。

## 一次评图怎样完成

1. 学生保存原图、材料、工艺、倍率和腐蚀剂，服务端创建学习轮次并冻结样本快照。修改图片或背景后，旧报告仍属于旧版本。
2. 点击“开始评图”后，前端提交持久任务。后端验证图片归属，读取真实图片字节，检索已发布教学资料，将图片、背景、规则和实际检索片段发送给配置的模型。
3. 模型按约定返回 JSON：四项分数与依据、缺陷及建议、可选位置、局限和引用。系统没有从一篇自然语言文章中用正则猜测评分。
4. 后端完整接收回复后校验 JSON 字段、四项规则、分数范围、引用和位置。格式不合格最多尝试一次修复；仍失败则记录失败，不生成演示报告填补结果。
5. 服务端重新计算总分，保存 AI 原稿、规则及样本快照、模型名和提示词版本。前端根据结构化字段展示评分表单。
6. 学生修改得分、个人规则文字或依据后，提交完整修正稿、修正理由和当前修订序号。后端再次校验并计算总分，新增修订记录；原始 AI 判断继续保留。

任务队列和 SSE 保存的是进度与结果状态。浏览器关闭不会取消任务；取消由专门接口处理。取消、超时、响应未正常结束或非法结果，不会保存为成功报告。重新分析与显式重试可能再次产生模型费用。

## 终端怎样查看 AI 调用

日志写到运行 Go 服务的终端标准错误流（stderr），与浏览器的进度信息分开。默认级别为 `info`、格式为 `text`，只记录调用关联信息、阶段、耗时和安全错误，不输出模型请求或回复正文。

本地排障需要查看正文时，在由运维维护的根目录 `.env` 中显式设置，再重启服务：

```dotenv
ZHIWEI_LOG_LEVEL=debug
ZHIWEI_LOG_FORMAT=text
ZHIWEI_LOG_AI_CONTENT=true
```

只有 `debug` 与 `ZHIWEI_LOG_AI_CONTENT=true` 同时生效才记录正文；单独开启任一个都不够。支持的级别为 `debug/info/warn/error`，格式为 `text/json`。排障结束后将内容开关设回 `false`，并恢复适合日常运行的级别。

`text`模式的正文有携带关联字段的块头、每行 `│` 前缀和end结束边界，便于在终端直接阅读；同一个正文片段不会和其它日志交错写入。`json`模式保持一行一个标准JSON日志对象，正文位于text字段，便于脚本过滤。

在前台执行 `make start`，日志随请求写到该终端。需要临时保存 JSON 日志时，先将 `ZHIWEI_LOG_FORMAT` 改为 `json`，再使用以下方式启动；这不会自动执行模型请求：

```sh
mkdir -p data/logs
umask 077
make -s start 2>data/logs/ai-debug.jsonl
```

在另一个终端执行 `tail -f data/logs/ai-debug.jsonl` 查看新记录。日志路径只是示例，不属于数据库表，也不会自动上传至第三方。不要在已有服务仍占用端口时再运行第二个实例。

定位一次请求时，先找 `job_id`，再按 `call_id` 和 `attempt` 区分第一次生成与格式修复。`request_id` 用于关联创建任务的 HTTP 请求。排队和两次模型调用属于不同耗时，不能简单把终端相邻两行之间的时间都算成模型响应时间。

| 日志消息 `msg` | 看什么 |
| --- | --- |
| `http.completed` | 请求关联ID、路由模板、HTTP状态与服务端处理耗时；响应头也提供X-Request-ID |
| `job.started` / `job.stage` / `job.finished` | 持久任务实际开始、阶段切换和终态 |
| `ai.call.started` / `ai.call.finished` | 调用序号、模型名称、耗时、结束原因和服务商实际返回的用量 |
| `ai.transport` | debug级别下的DNS/TCP/TLS、连接复用、请求发送及首个HTTP响应字节等节点 |
| `ai.validation` / `ai.repair` | 结构校验结果、错误字段路径与原因分类，以及是否进行唯一一次修复 |
| `ai.content` | 双开关启用后的脱敏正文，按call_id/direction/part分段 |
| `ai.content.omitted` | 任务正文预算已经用完，说明本次省略的方向、字节数与原因 |

首个HTTP响应字节和首次模型内容不是同一指标：`first_response_byte`可能只是响应头，`first_content_ms`以收到实际回复内容为准。二者都不能单独代表完整分析已完成。

正文以分段日志输出，单次模型调用的请求方向与响应方向各限制32 KiB；超出时保留最多24 KiB头部及8 KiB尾部，并为截断标记留出空间。每个正文片段最多4 KiB，同一任务的正文总预算为128 KiB。限制按UTF-8字节计算，日志外围的时间、字段名和JSON转义不属于正文预算。通过 `direction` 与 `part` 恢复同一次调用的分段顺序；`original_bytes/omitted_bytes`及截断标记帮助识别缺失。截断后的日志不等于完整模型请求/回复，也不能拿日志代替报告存档。

日志脱敏覆盖配置密钥、敏感键值、图片 data URL、长 Base64、`think` 块及控制字符；不记录 HTTP 认证头、Cookie 或图片原始数据。正文开关仍可能输出材料背景、检索片段和模型教学解释等业务文本，脱敏不等同于对任意自由文本做完整匿名化。排障分享应只保留所需任务片段，不附 `.env`。

## 页面进度与耗时怎样理解

任务接口返回实际阶段，而不是定时模拟“已完成百分之几”。可出现排队、准备图片、检索资料、等待模型、接收回复、校验、一次修复、保存，以及成功/失败/取消；文档导入另有提取和切片阶段。

SSE 的 `progress` 事件提供 `{code,label,at,elapsed_ms,attempt?,completed?,total?}`。事件仍使用标准 `id/event/data`，支持断线回放。进度不携带未校验的模型正文；最终报告从任务的 `result_id` 读取。旧版 `delta:{text}` 阶段事件继续兼容。

学习页面显示阶段时间线、“已等待/已进行”时间，报告展示生成时间和“分析耗时”；具体模型信息留在管理员配置及服务端溯源中。结果已经生成但读取失败时使用“重新读取结果”，只重读已保存结果，不再次调用模型。“重新分析”则创建新任务，两种操作不同。

任务的 `progress_history` 保留实际阶段，`timings` 记录以毫秒为单位的阶段及模型调用耗时：`queue_ms` 是排队时间，`total_ms` 是处理开始至提交结果前的计时快照，不包含排队和最终数据库提交；`model_ms` 是实际模型调用的累计耗时，`model_calls` 可区分正常生成与格式修复。服务商未返回 token 用量时，相关字段缺省，不猜测数量或费用。旧报告没有计时字段时显示“分析耗时 —”，不能当成零毫秒；其它未记录的业务字段仍按各自语义提示。

已开始任务被取消时保存当时实际采集的计时，model_ms也可包含尚未返回的模型调用截至取消瞬间已经消耗的时间；这不是该调用未来完整耗时或费用。仍在排队就取消，或进程中断后已失去内存测量的任务，可以没有timings；系统不会用updated_at推算出一份看似完整的耗时。文档导入的completed/total仅表示已整理片段数，按0/N、N/N报告实际结果。

## 模型 JSON 与评分表单

一次评图的单项数据类似下面这样。此处只展示一个项目，实际模型报告必须包含四项：

```json
{
  "id": "scratches",
  "label": "划痕",
  "score": 20,
  "max_score": 25,
  "evidence": "当前视场存在需复核的线性痕迹。"
}
```

固定项目是 `scratches`（划痕）、`artifacts`（假象）、`etching`（侵蚀程度）、`clarity`（组织清晰与正确度），每项25分。各项分数由模型结合规则建议；服务端负责检查合法性并求和，没有从像素自动计算出四项得分的确定性公式。

例如四项为20、23、21、22，服务端总分是86。如果第三项无法观察，则其 `score:null`，总分也为 `null`，可判断覆盖率为0.75。未知不能被强制换成零分，也不能把三项分数折算为“百分制总分”。

前端把 JSON 字段绑定到输入框、规则文字和依据文本。修改时的总分预览仅供界面显示，保存后的权威数值由后端重算。首次修正使用 `base_version:0`，以后提交当前 `revision_no`；版本过期返回409，避免覆盖另一窗口刚保存的内容。

修正只影响本人的学习记录，不发布公共规则，不自动训练模型。报告 `data` 和 `original_data` 保留 AI 原稿，`latest_revision.data` 保存当前学生版本，历史修订可单独查询。教师查看、指导和明确复核另存记录，均不替代实际制样与实验验证。

## 为什么可以在图片上画框

矩形来自模型输出的 `defects[].bbox`。后端没有另外调用检测算法来寻找这些位置。坐标使用原始图片的比例：左上角为原点，`x/width` 按图片宽度归一化，`y/height` 按图片高度归一化。

```json
{
  "name": "待核对线性痕迹",
  "severity": "uncertain",
  "evidence": "该区域存在近似平行线条，需结合其它视场核对。",
  "suggestion": "下一轮比较抛光前后同类视场。",
  "bbox": { "x": 0.1, "y": 0.2, "width": 0.3, "height": 0.2 }
}
```

这表示从图片宽度的10%、高度的20%处开始，框宽占30%、框高占20%。若原图为1000×800像素，对应矩形左上角是(100,160)，宽300、高160像素。前端将四个值乘以100%，覆盖在保持原图比例的图片容器上；缩放页面不需要重新识别图片。

鹰眼页使用红色编号框，可显示/隐藏，点击对应问题会突出该框。框编号沿用完整问题列表的位置；部分问题没有坐标时不把其它框重新编号。红色是统一定位样式，不单独表示问题严重程度。前端还会拒绝非有限数字、负宽高或越界框，不为缺坐标问题编造位置。

框只是模型认为值得观察的大致区域，不是缺陷轮廓或相区分割。模型可以省略 `bbox`；没有框不代表没有问题。后端能拒绝越界、负宽高等非法坐标，无法仅凭坐标证明框内确有缺陷。密集纹理、细长划痕、倍率不足或模型视觉输入异常，都可能影响定位。

当前评分表单不提供拖框编辑。即使直接提交修改了bbox的修正JSON，后端也只给与原稿同序同名的缺陷保留有效原框，其它条目移除位置；不能通过学生修正把自定义坐标冒充AI定位。

## 结构检查的边界

- 调用使用兼容 Chat Completions 接口，并请求 `response_format: {"type":"json_object"}`；具体字段及业务规则由本项目 Go 校验器执行，并非依赖服务商一定支持 JSON Schema 严格输出。
- 拒绝未知字段、重复 JSON 键、多个拼接 JSON 对象、缺失必需字段、越界分数和不属于实际检索片段的引用；五维报告要求成分、工艺、组织、性能、应用齐全。
- 五维依据类型为 `known/observed/inferred`，分别代表已知背景、图片观察和待验证推断。已知材料不能单独证明图片里一定有某种组织。
- 只接受正常结束的模型回复。半截 JSON、内容过滤、拒答和超时不会因“已输出一些文字”而被认定成功。
- 引用 ID 有效表示资料确实被检索到；它本身不保证资料与结论的专业因果关系成立。学习评分、组织判断、引用质量仍需要教师和真实样本核对。

## 超时预算

每次HTTP模型请求独立使用ZHIWEI_AI_TIMEOUT_SECONDS，默认300秒，等待响应头不再额外限制为60秒。仅结构校验失败时最多发起一次格式修复，修复获得独立预算；生成总预算最多两次调用。网络超时/取消/拒绝/截断不会触发格式修复。失败以timeout及中文原因持久化，不生成伪成功报告。旧context deadline exceeded文本在界面也转换为可读提示。

提示词版本metallography-v4明确五维数组及字符串类型；一次格式修复携带当前任务的完整契约和安全的字段路径/原因代码，不混入其他报告字段。类型不符、未知字段、缺失字段会被拒绝，不能通过丢字段或猜测内容形成成功报告。


## 参考图谱与教师案例

本次请求先读取当前样本，再按材料、工艺、已知判断及问题做关键词召回。文档仍最多6个片段；已发布参考图谱和可见教师案例最多2张图片。所有资料进入同一个FTS5词项索引，用BM25排序，不调用embedding、不执行图片相似度检索。

请求中的图片按“当前待分析图片 → 带资料编号的参考图片”排列；评分和bbox只针对第一张。参考图谱的来源、观察依据和背景与图片一起提供。案例仅在所关联班级轮次中使用，管理员公开后可参与个人练习；没有匹配资料时不补充预置内容。

教师明确复核仅绑定某个修订号与样本版本；需另行整理、发布匿名案例，才成为检索资料。案例包含教师结论与依据，不向模型提供学生账号和原报告入口。发布资料不训练模型。

progress.details只传图片元数据、来源标题、计数、请求时刻、实际接收量和校验状态。stage_id标识同一次阶段，同阶段详情更新不会改变at/elapsed_ms或产生新步骤；流式接收计数最多每秒更新一次，结束时保存最终计数。模型正文仅在开启服务端日志时脱敏输出到终端。
